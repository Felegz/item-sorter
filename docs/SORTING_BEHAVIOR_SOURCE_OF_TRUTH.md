# SOURCE OF TRUTH: функции сортировки и их фактическое поведение

Этот документ — обязательный источник истины перед любым изменением сортировки,
фильтрации, слияния массивов, вставки задач или разбора секций главного списка.

## Главное правило будущих изменений

Менять только одну функцию или один замкнутый вызовный контур за раз.

Перед изменением:

1. Зафиксировать старый вход, ответы пользователя, последовательность сравнений
   и результат characterization-тестом.
2. Изменить только выбранную функцию и необходимые ей тесты.
3. Доказать, что остальные пользовательские команды дают прежний результат.
4. Не совмещать переименование, смену структуры данных и изменение алгоритма.

## Общий контракт сравнения

### `compareTasks(task1, task2, progress = null)`

Показывает SweetAlert2-диалог с двумя задачами.

- Возвращает Promise со значением `-1`, если пользователь выбрал `task1`.
- Возвращает `1`, если пользователь выбрал `task2`.
- Значение `0` пользовательский интерфейс не возвращает.
- Увеличивает глобальный счётчик сравнений `counter`.
- При переданном `progress` увеличивает `progress.done` и показывает прогресс.
- Диалог нельзя закрыть кликом снаружи или Escape.
- В восстановленной версии текст задачи вставляется в HTML как сырой текст. Это
  часть восстановленного состояния, а не рекомендация для будущего безопасного
  рендеринга. Исправлять рендерер нужно отдельным шагом, не меняя результат
  сравнения и порядок вызовов.

## Sort Tasks: точный пользовательский сценарий

### `parseAllSections(text)`

Этот парсер принадлежит только Sort Tasks. Он не является универсальным
парсером пяти списков.

Он возвращает:

| Поле | Какие строки попадают |
|---|---|
| `newTasks` | активные строки выше первого `SORTED (...)` |
| `sortedTasks` | активные строки после `SORTED (...)` и до `PARTIALLY SORTED` или игнорируемого блока |
| `partiallySorted` | активные строки после `PARTIALLY SORTED` и до игнорируемого блока |
| `tail` | все строки начиная с `ИГНОРИРУЕМЫЕ ЗАДАЧИ`, без преобразования |

Для первых трёх массивов пустые строки, любые известные маркеры и строки,
начинающиеся с `x `, отбрасываются. `tail` сохраняется как массив исходных строк.

### `sortTasks()`

Порядок действий нельзя менять без отдельного продуктового решения:

1. Сохраняет текущее поле через `saveDataToLocalStorage()`.
2. Разбирает документ функцией `parseAllSections()`.
3. Если одновременно существуют `sortedTasks` и `partiallySorted`, предлагает
   проверить хвост.
4. При согласии вызывает `promoteTailCandidates()`.
5. Берёт для новой сортировки только `newTasks`.
6. Если новых задач не больше 60, полностью сортирует их через `mergeSort()`.
7. Если новых задач больше 60, вычисляет
   `min(50, ceil(newTasks.length * 0.2))` и извлекает это количество через
   `partialSortTasks()`.
8. Собирает новый основной блок как `winners + currentSorted`. Новая партия
   целиком ставится перед старым SORTED. Между новой партией и старым SORTED
   дополнительных сравнений нет.
9. Собирает частичный блок как `losers + workingPartially`.
10. Создаёт новые заголовки `SORTED (YYYY.MM.DD)` и
    `PARTIALLY SORTED (YYYY.MM.DD)` только для непустых блоков.
11. Добавляет сохранённый `tail` в конец.
12. Записывает результат через `parts.join('\n')`, сохраняет его и обновляет
    приоритеты/подсветку/фильтры, если соответствующие функции существуют.

Sort Tasks не читает `NEW ARRAY` как отдельную новую партию, не создаёт его и не
выполняет глобальное слияние новой партии со старым SORTED.

### `promoteTailCandidates(sortedTasks, partiallySorted)`

Функция предполагает, что начало `partiallySorted` идёт от более важных задач к
менее важным.

1. Берёт только первый ещё не проверенный кандидат хвоста.
2. Сравнивает его с последней, то есть наименее важной, задачей текущего SORTED.
3. Если кандидат проиграл, функция немедленно прекращает проверку. Более поздние
   элементы хвоста не проверяются.
4. Если кандидат выиграл, бинарным поиском находит его позицию внутри SORTED,
   вставляет и переходит к следующему элементу хвоста.

Возвращает `{ sortedTasks, partiallySorted, promoted }`.

### `mergeSort(tasks)` и `merge(left, right)`

`mergeSort` рекурсивно делит новую партию пополам. `merge` сравнивает первые ещё
не использованные элементы обеих половин и формирует порядок от более важного к
менее важному. Текст задач и количество элементов не меняются.

### `partialSortTasks(tasks, n)` и `heapifyDown(...)`

`partialSortTasks` работает с копией входного массива:

1. Строит max-heap, где корень — выбранная пользователем наиболее важная задача.
2. Извлекает не более `n` верхних задач в массив `sorted`.
3. Возвращает остаток внутреннего heap-массива как `remaining`.

`remaining` не является полностью линейно отсортированным списком. Однако
восстановленная `promoteTailCandidates` всё равно останавливается после первого
проигрыша — это фактическое поведение `99cf747`, а не новый вывод о корректности.

## Merge Arrays: точный пользовательский сценарий

### `parseArrays(text)`

Этот парсер принадлежит только Merge Arrays.

- `first`: все строки до первого точного маркера `NEW ARRAY`; если маркера нет —
  весь документ.
- `second`: строки после `NEW ARRAY` и до
  `НЕУПОРЯДОЧЕННЫЕ ЗАДАЧИ`; если второго маркера нет — до конца.
- `tail`: все строки начиная с `НЕУПОРЯДОЧЕННЫЕ ЗАДАЧИ`, включая маркер.

### `mergeArraysUI()`

1. Сохраняет текущее поле.
2. Разбирает его через `parseArrays()`.
3. В `first` и `second` удаляет пустые строки и все известные маркеры.
4. Сливает оставшиеся задачи через `mergeGalloping()`.
5. Записывает `merged + NEW ARRAY + tail`.
6. Снова сохраняет поле.

После успешного merge маркер `NEW ARRAY` остаётся в документе, даже когда блок
под ним пуст. Это исторический результат функции.

### `mergeGalloping`, `gallopRight`, `gallopLeft`

`mergeGalloping` принимает два уже упорядоченных массива и последовательно
выбирает более важный первый элемент. После семи последовательных побед одной
стороны функции `gallopRight` или `gallopLeft` ищут границу серии бинарным
поиском, чтобы скопировать несколько элементов сразу.

Эти функции не сортируют произвольные массивы с нуля. Корректность результата
зависит от того, что оба входных массива уже упорядочены одинаковым способом.

## Filter Tasks: точный пользовательский сценарий

### `filterTasksUI()`

1. Сохраняет текущее поле.
2. Делит весь документ по переводам строк и табам.
3. Удаляет все известные маркеры и старые отображаемые строки форматов
   `(A)`, `added ... ago`, `added yesterday`, `Due...`.
4. Удаляет пустые и выполненные строки, начинающиеся с `x `.
5. Удаляет точные дубликаты через `Set`, сохраняя первое вхождение.
6. Передаёт задачи в `filterTasks()`.
7. Полностью пересобирает документ как выбранные задачи, затем новый заголовок
   `ИГНОРИРУЕМЫЕ ЗАДАЧИ YYYY.MM.DD`, затем проигнорированные задачи.
8. Записывает результат через `result.join('\n\n')` и сохраняет.

Историческая функция не сохраняет прежнее распределение активных задач по
секциям. Выполненные задачи исключаются до пересборки и поэтому могут исчезнуть
из результата. Это опасное, но фактическое поведение эталона; исправлять его
можно только отдельным изменением с отдельным тестом и решением владельца.

### `filterTasks(tasks)`

Последовательно вызывает `chooseWindow` для каждой задачи:

- `include` → отредактированный текст добавляется в `tasksToSort`;
- `ignore` → отредактированный текст добавляется в `ignoredTasks`;
- `delete` → задача не попадает ни в один результат.

Функция не прекращает цикл после отдельного решения.

## Insert Unsorted Tasks: точный пользовательский сценарий

`promptUnsortedTasks()` и `insertUnsortedClickHandler()` отвечают только за ввод
строк и запуск `insertUnsortedTasksUI()`.

### `insertUnsortedTasksUI(unsortedTasks)`

1. Сохраняет текущее поле.
2. Находит первый маркер `ИГНОРИРУЕМЫЕ ЗАДАЧИ`.
3. Берёт все строки выше него как `upperLines`.
4. Собирает все маркеры из `upperLines` отдельно в `markerLines`.
5. Все остальные непустые строки выше игнорируемого блока считает единым
   упорядоченным массивом `sorted`. Сюда могут попасть задачи из разных секций.
6. Для каждой введённой задачи выполняет встроенный бинарный поиск с
   `await compareTasks(...)` и вставляет её в найденную позицию.
7. Записывает `markerLines + sorted + пустая строка + исходный ignored tail`.

Функция содержит собственный бинарный поиск с `await compareTasks(...)`.
Перемещение всех маркеров в начало `upperLines` — историческое поведение, даже
если документ содержит несколько секций.

## Что существует рядом, но не является эталоном старых кнопок

В проекте остаются `parseTaskDocument`, `serializeTaskDocument` и модуль
`TaskListOperations`. В нём сохранены только более поздние возможности, включая
добавление задачи наверх, дату создания и сортировку одной задачи на странице
`/tasks`; альтернативного контура массовой сортировки в модуле больше нет.

Их наличие не разрешает переводить четыре восстановленные команды на общую
пятисписочную модель одним большим рефакторингом. Такая миграция выполняется
только по одной команде с доказательством эквивалентности её старому поведению
или с явно согласованным изменением продукта.

## Обязательная проверка при следующей адаптации

Для выбранной функции тест должен проверять не только итоговый массив, но и:

- точные входные границы секций;
- порядок и пары задач, показанные в сравнениях;
- момент остановки сравнений;
- расположение всех маркеров после записи;
- сохранение или намеренное удаление каждой исходной строки;
- поведение при пустых секциях;
- количество и положение одинаковых строк;
- отсутствие изменений в остальных командах.
