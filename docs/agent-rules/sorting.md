# Правила изменения списков и сортировки

Читайте этот файл перед изменением парсинга, секций, сортировки, фильтрации,
слияния, вставки задач или полной пересборки task-документа.

Фактическое поведение восстановленных функций описано только в
`../SORTING_BEHAVIOR_SOURCE_OF_TRUTH.md`. Этот файл задаёт порядок безопасной
работы, но не переопределяет продуктовые контракты из источника истины.

## Сначала зафиксировать существующее поведение

- Не выводить назначение функции из названия переменной, маркера или документа,
  написанного ИИ.
- Перед изменением найти работающую реализацию и историю целевой функции в Git.
- Если запрос называется «унифицировать», «отрефакторить» или «переименовать»,
  это не разрешает менять входы, выходы, область действия или порядок действий.
- До рефакторинга написать characterization-тесты на установленное поведение.
  Тест, написанный после придуманного изменения, не доказывает корректность.
- Если код, Git-история и слова владельца задают разные варианты поведения,
  остановиться и попросить владельца определить продуктовый контракт.

## Обязательные свойства данных

- Более поздняя модель содержит пять списков: `inboxUnsorted`, `inboxSorted`,
  `sorted`, `partiallySorted`, `ignored`. Восстановленные старые команды пока не
  используют эту модель и имеют разные собственные правила разрезания текста,
  кроме отдельно адаптированной `mergeArraysUI()`.
- Канонический маркер `inboxSorted` — `INBOX SORTED`. Старое имя `NEW ARRAY`
  допускается только на чтение и должно мигрировать при записи. Нельзя удалять
  legacy-распознавание, пока существуют старые локальные и Dropbox-копии.
- Не переводить старую команду на `parseTaskDocument()`, `TaskListOperations`
  или `formatTaskList()` без отдельного пофункционального шага и
  characterization-теста. Даже общая сериализация меняет исторический результат.
- Целевое безопасное поведение не должно менять текст задач, удалять дубликаты
  или терять выполненные задачи. При этом источник истины отдельно отмечает
  места, где старый код этому правилу не соответствует. Такие места исправляются
  только как явно согласованное изменение, а не скрыто внутри рефакторинга.
- Перед записью результата проверить сохранность всех затрагиваемых строк и
  маркеров. Тесты должны содержать задачи во всех секциях, которые читает
  выбранная функция, и выполненную задачу.
- Реальный список из `private-test-data/default-tasks.txt` нельзя коммитить,
  загружать, цитировать или показывать на скриншотах.

## Текущие продуктовые контракты

- Исторические контракты четырёх команд и действующий адаптированный контракт
  Merge Arrays находятся в `../SORTING_BEHAVIOR_SOURCE_OF_TRUTH.md`.
- `mergeArraysUI()` — единственная старая команда, переведённая на
  `parseTaskDocument()` и `serializeTaskDocument()`. Она объединяет только
  `sorted + inboxSorted`; расширять область операции без решения владельца
  запрещено.
- Сортировка одной задачи на странице задач — более поздняя отдельная функция.
  Она помещает конкретный экземпляр в `sorted`; одинаковый текст у нескольких
  задач не должен приводить к удалению другой задачи.
- Не использовать заявления из старых версий `Project Structure.md` или
  `PROJECT_STATE.md` как доказательство поведения. Проверять функцию по коду,
  эталонному коммиту и characterization-тесту.

## Проверка изменения

- Перед первой адаптацией конкретной восстановленной функции добавить тест её
  входа, результата и последовательности пользовательских сравнений из
  `99cf747`.
- Запустить `node tests/format-task-list.test.cjs`.
- Запустить `node tests/task-list-model.test.cjs` и
  `node tests/sorting-pipeline.test.cjs`, если они существуют.
- Выполнить `node --check` для каждого изменённого JavaScript-файла.
- Для изменения пользовательского сценария воспроизвести конкретную кнопку на
  копии списка. Автотесты не заменяют интерактивную проверку диалогов сравнения.
- Не расширять набор проверок после успешного целевого прогона без новой причины.
